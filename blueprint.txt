# 3. STORAGE RESPONSIBILITIES

## FAISS

FAISS stores vector indexes.

### RAG FAISS

Contains:

```text
child chunk embeddings
+
child IDs
```

### Cache FAISS

Contains:

```text
cache-question embeddings
+
cache IDs
```

FAISS is not the source of the actual answer text.

---

# 4. SQLITE

SQLite is the persistent RAG document/chunk store.

It contains:

```text
Parent text
Child text
Parent metadata
Child metadata
Document metadata
```

The exact metadata contract already agreed for the project should be preserved.

SQLite is primarily used on the **RAG path**.

A cache HIT should not need SQLite.

---

# 5. REDIS

Redis is the runtime cache store.

Conceptually:

```text
cache_id
    ↓
{
    question,
    canonical_question,
    answer,
    chapter,
    section,
    subsection,
    citations,
    textbook_version,
    metadata
}
```

FAISS finds the matching `cache_id`.

Redis retrieves the actual cached answer.

The application/backend is the glue; FAISS, Redis and SQLite do not directly communicate with each other.

---

# 6. EMBEDDINGS

Use local Hugging Face embeddings.

Current baseline:

```text
sentence-transformers/all-MiniLM-L6-v2
```

Use the same embedding space consistently for:

### RAG

```text
child chunks → embeddings → FAISS
```

### Cache

```text
canonical cache questions → embeddings → cache FAISS
```

### Query

```text
user query → embedding → search appropriate FAISS index
```

Do **not** use OpenAI embeddings.

Do **not** introduce a remote embedding API.

Reason: the project should use a free/local embedding model and avoid unnecessary network latency on the cache critical path.

# 7. CHUNKING

The current agreed design is:

```text
NCERT Chapter
    ↓
Section / Subsection identification
    ↓
Recursive splitting INSIDE the logical section
    ↓
Parent chunks
    ↓
Child chunks
```

Do **not** recursively split the entire PDF first and attempt to reconstruct sections afterward.

### Baseline

```text
Parent:
1500 tokens
200 token overlap

Child:
400 tokens
80 token overlap
```

These are **baseline values only**.

They must later be evaluated with actual retrieval quality.

Do not change them silently.

# 10. CACHE SEMANTICS

The cache embedding represents the **question/doubt**.

It should NOT primarily embed:

- the answer
- only the chapter heading
- only the section heading

The purpose is semantic question matching.

Example:

```text
"What is refraction?"
"What does refraction mean?"
```

→ should potentially map to the same cached canonical question.

But:

```text
"Image formation by concave mirror"
"Image formation by convex mirror"
```

→ should not be treated as the same question merely because the wording is similar.

Similarly:

```text
"Focal length when R = 20 cm"
"Focal length when R = 30 cm"
```

→ should not blindly reuse the same numerical answer.

These behaviors are explicitly required by the assignment. AI_Intern_Assignment_Prepzy

---

# 11. CACHE RETRIEVAL

Use:

```text
Incoming query
    ↓
Local embedding
    ↓
Cache FAISS Top-K
    ↓
Reranker
    ↓
Similarity / relevance threshold
    ↓
HIT or MISS
```

Cache matching should prioritize **precision over recall**.

Reason:

```text
False miss:
extra LLM call

False hit:
potentially wrong educational answer
```

Do not hardcode an arbitrary threshold without evaluation.

The threshold must eventually be calibrated against representative positive/negative examples.

# 12. CACHE ID

Current agreed approach:

```text
UUID5(
    namespace,
    textbook_version + ":" + canonical_question
)
```

Purpose:

- deterministic
- reproducible
- same canonical question + same textbook version → same ID
- different textbook version → different ID

The ID is only an identifier.

It is not the semantic matching mechanism.

# 14. RUNTIME CACHE WRITE

A cache MISS must **not automatically result in a cache write**.

Correct flow:

```text
Cache MISS
    ↓
RAG
    ↓
LLM
    ↓
LLM Verifier
    ↓
Pass?
 /   \
YES   NO
 ↓     ↓
Cache  Don't cache
```

The current pragmatic validator is an **LLM verifier**.

It should check:

1. Does the answer answer the question?
2. Is it supported by retrieved NCERT context?
3. Is the evidence/citation appropriate?
4. Did the model introduce unsupported textbook-external claims?
5. Is the question suitable for reusable caching?

The verifier is a **safety gate**, not a mathematical guarantee of correctness.

Do not claim otherwise.
